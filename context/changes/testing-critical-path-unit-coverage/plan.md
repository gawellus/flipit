# Critical-Path Unit Coverage Implementation Plan

## Overview

Bootstrap Vitest from zero and write unit tests protecting the three highest-priority risks at the cheapest test layer: LLM response parsing failures (Risk #1), CRUD service edge cases (Risk #4), and Zod input validation boundaries (Risk #5). Includes a targeted production fix — adding min/max length enforcement to `parseFlashcards` — to close a validation gap between generation and save time before tests lock in the contract.

## Current State Analysis

Zero test infrastructure exists. No Vitest dependency, no config, no test files, no test scripts. The codebase has nine Zod schemas across five endpoint files, four CRUD service functions with dependency-injected Supabase clients, and a private `parseFlashcards` function that manually validates LLM output without length constraints.

### Key Discoveries:

- `parseFlashcards` is not exported (openrouter.ts:58) — must be exported for direct pure-function testing
- All 9 Zod schemas are `const` (not exported) inside endpoint files — must be exported to test without re-creating them
- `astro:env/server` is a virtual module that only exists at Astro build time — Vitest must alias it to a mock module
- `@/*` path alias (tsconfig.json:9-10) must be replicated in Vitest config via `resolve.alias`
- CRUD service functions accept `SupabaseClient` as first parameter — testable with a chainable mock, no module mocking needed
- `parseFlashcards` accepts empty strings and has no max-length check on front/back — SaveFlashcardsSchema enforces max 2000 at save time, but generation can produce strings that will fail at save (openrouter.ts:88-89 only checks `typeof === "string"`)

## Desired End State

Running `npm test` executes a full unit test suite covering:

- Every error path and edge case in LLM response parsing (including the new length constraints)
- All four CRUD service functions with mocked Supabase client (error propagation, empty input, ILIKE escaping, NotFoundError)
- Boundary tests for all 9 Zod schemas (min/max, type coercion, cross-field refinements)

All tests are co-located with source files, run in under 5 seconds, require no external services, and the test-plan cookbook (§6.1, §6.2) documents the patterns for future contributors.

**Verification**: `npm test` exits 0 with all tests passing; `npm run lint` and `npm run build` still pass.

## What We're NOT Doing

- **Auth endpoint Zod validation**: `signin.ts` and `signup.ts` have no server-side Zod validation — a real Risk #5 gap, but adding schemas is a production code change outside Phase 1 scope. Deferred; will be visible to Phase 2 or a dedicated change.
- **Integration tests**: No real Supabase, no real fetch, no RLS verification — that is Phase 2 (Risks #2, #3, #6, #7).
- **CI gate wiring**: Tests run locally only. Adding `npm test` to GitHub Actions is Phase 3.
- **UI/component tests**: Out of scope per test-plan §7.
- **Refactoring schemas to a shared module**: Schemas stay inline in endpoint files; tests use `vi.mock` for transitive Astro dependencies.
- **Mutation testing (Stryker)**: Can be applied selectively after this phase ships, per CLAUDE.md guidance. Not part of the plan.

## Implementation Approach

Six phases, ordered by dependency: infrastructure first (Phase 1), then minimal production changes for testability (Phase 2), then one test file per risk area (Phases 3-5), then cookbook sync (Phase 6). Each test phase is independent after Phase 2 and can be implemented in any order, but the plan orders them by risk priority (#1 → #4 → #5).

All test files are co-located with their source (`*.test.ts` next to the module under test). The `astro:env/server` virtual module is handled via a centralized resolve alias in vitest.config.ts pointing to a mock file, so individual tests never need to mock it themselves.

## Critical Implementation Details

### `astro:env/server` mocking strategy

`astro:env/server` is a virtual module generated by Astro at build time. Three files import from it: `openrouter.ts` (OPENROUTER_API_KEY, OPENROUTER_MODEL) and `supabase.ts` (SUPABASE_URL, SUPABASE_KEY). Any test that transitively imports these modules — including Zod schema tests that import from endpoint files — will fail without a mock.

The mock is a single `.ts` file exporting all four env vars with test values. Vitest's `resolve.alias` maps `astro:env/server` → this file globally, so no per-test `vi.mock()` is needed for this module. This is configured once in Phase 1 and never touched again.

## Phase 2: Testability Changes & parseFlashcards Hardening

### Overview

Make three targeted production code changes: export `parseFlashcards` for direct testing, export all 9 Zod schemas from their endpoint files, and add min/max length enforcement to `parseFlashcards` to close the validation gap between generation and save time.

### Changes Required:

#### 1. Export `parseFlashcards`

**File**: `src/lib/services/openrouter.ts:58`

**Intent**: Make `parseFlashcards` a named export so tests can call it directly as a pure function, without mocking `fetch` or env vars.

**Contract**: Change `function parseFlashcards` to `export function parseFlashcards` at line 58. No other changes.

#### 2. Add length validation to `parseFlashcards`

**File**: `src/lib/services/openrouter.ts:82-96`

**Intent**: Filter out items with empty or oversized front/back strings during LLM response parsing. This aligns generation-time validation with SaveFlashcardsSchema (min 1, max 2000) so users never see cards in review that will fail to save.

**Contract**: The existing filter condition (lines 83-89) already checks `typeof front === "string"` and `typeof back === "string"`. Extend it to also require: `front.trim().length >= 1`, `back.trim().length >= 1`, `front.length <= 2000`, `back.length <= 2000`. Items failing these checks are silently filtered, matching the existing pattern for invalid items. The max limit (2000) matches `SaveFlashcardsSchema`'s `max(2000)` constraint.

#### 3. Export Zod schemas from endpoint files

**Files**:

- `src/pages/api/generations.ts:5` — `GenerateRequestSchema`
- `src/pages/api/flashcards.ts:7,29,35,46` — `SaveFlashcardsSchema`, `ListQuerySchema`, `UpdateFlashcardSchema`, `DeleteFlashcardSchema`
- `src/pages/api/collections.ts:7,11` — `CreateCollectionSchema`, `DeleteCollectionSchema`
- `src/pages/api/study/[id].ts:6` — `ParamsSchema`
- `src/pages/api/study/review.ts:7` — `ReviewSchema`

**Intent**: Make schemas importable by test files so tests verify the actual production schemas, not copies.

**Contract**: Add `export` keyword to each `const` declaration. No other changes to schema definitions or endpoint logic.

#### Automated Verification:

- `npm run build` passes (exports don't break Astro build)
- `npm test` still passes (smoke test from Phase 1)

## Phase 3: Risk #1 — LLM Parsing Unit Tests

### Overview

Write comprehensive unit tests for `parseFlashcards` (pure function, ~15 scenarios) and `generateFlashcards` (mocked fetch, ~6 scenarios). These tests defend against LLM returning invalid, malformed, truncated, or empty responses.

### Changes Required:

#### 1. `parseFlashcards` test suite

**File**: `src/lib/services/openrouter.test.ts` (expand smoke test from Phase 1)

**Intent**: Test every parsing path identified in research, plus the new length validation from Phase 2. `parseFlashcards` is a pure function — no mocking needed.

**Contract**: `describe("parseFlashcards", ...)` with test cases covering:

_Happy paths (oracle: SYSTEM_PROMPT contract + code lines 67-74):_

- Valid `{"flashcards":[{"front":"Q","back":"A"}]}` → returns `[{front:"Q",back:"A"}]`
- Valid direct array `[{"front":"Q","back":"A"}]` → same result
- Items with extra fields `{front,back,hint}` → returns only `{front,back}`
- Mix of valid and invalid items → returns only valid ones

_Error paths (oracle: explicit throws in code):_

- Invalid JSON string → throws "Failed to parse LLM response as JSON"
- Truncated JSON → throws "Failed to parse LLM response as JSON"
- Wrong wrapper key `{"cards":[...]}` → throws "LLM response is not a flashcard array"
- Empty array `{"flashcards":[]}` → throws "LLM response contained no valid flashcard proposals"
- All items invalid → throws "no valid flashcard proposals"
- `null`, `"string"`, `42` as parsed value → throws "not a flashcard array"

_Silent filtering (oracle: filter condition lines 83-96):_

- Items with wrong keys `{"question":"Q","answer":"A"}` → filtered
- Items with `front: 123` (non-string) → filtered
- Items with empty front `""` → filtered (Phase 2 fix)
- Items with whitespace-only front `"  "` → filtered (Phase 2 fix)
- Items with front > 2000 chars → filtered (Phase 2 fix)
- Items with empty back → filtered (Phase 2 fix)
- Items with back > 2000 chars → filtered (Phase 2 fix)

#### 2. `generateFlashcards` test suite

**File**: `src/lib/services/openrouter.test.ts`

**Intent**: Test the fetch-wrapper function with mocked global `fetch`. Each test verifies a specific error path or delegation to `parseFlashcards`.

**Contract**: `describe("generateFlashcards", ...)` using `vi.stubGlobal("fetch", ...)` or `vi.spyOn(globalThis, "fetch")` for fetch mocking. The `astro:env/server` mock from Phase 1 provides `OPENROUTER_API_KEY` and `OPENROUTER_MODEL`. Test cases:

- API key missing (mock `OPENROUTER_API_KEY` as empty) → throws "not configured"
- Fetch returns non-200 status → throws "OpenRouter API error ({status}): {body}"
- Response has empty `choices` array → throws "empty response"
- Response has `choices[0].message` with null content → throws "empty response"
- Valid response with parseable content → returns `FlashcardProposal[]`

For the "API key missing" test, override the mock module value using `vi.mock` within the test or a separate describe block that re-mocks `astro:env/server` with an empty key.

### Success Criteria:

#### Automated Verification:

- `npm test -- openrouter.test.ts` passes with all scenarios green
- `npm run lint` passes
- No test uses the same logic as the implementation to compute expected values (anti-pattern: mirror implementation)

#### Manual Verification:

- None — pure-function and mock-only tests

**Implementation Note**: After completing this phase and all automated verification passes, proceed to Phase 4.

## Phase 4: Risk #4 — CRUD Service Edge-Case Tests

### Overview

Write unit tests for all four service functions in `flashcards.ts` with a mocked Supabase client. Tests verify error propagation, empty-input guards, ILIKE wildcard escaping, NotFoundError mapping, and pagination computation.

### Changes Required:

**File**: `src/lib/services/flashcards.test.ts`

**Intent**: Create a reusable mock factory for the `SupabaseClient` that supports the chainable query builder pattern (`.from().insert().select()`, `.from().select().eq().order().range()`, etc.).

**Contract**: A helper function (local to the test file or in a shared test utility if needed) that returns a mock `SupabaseClient` with `vi.fn()` methods. Each test configures the mock's return value to simulate success, error, or specific Supabase responses. The mock must support chaining — each method returns an object with the next method in the chain.

#### 2. `createFlashcards` tests

**File**: `src/lib/services/flashcards.test.ts`

**Intent**: Test the empty-array guard and error propagation.

**Contract**: `describe("createFlashcards", ...)` with:

- Empty cards array → returns `[]`, no `.from()` call on the mock (oracle: guard at line 10-12)
- Supabase insert error → throws "Failed to insert flashcards: {msg}" (oracle: lines 24-26)
- Successful insert → returns data from mock (happy path)

#### 3. `listFlashcards` tests

**File**: `src/lib/services/flashcards.test.ts`

**Intent**: Test pagination computation, ILIKE escaping, and search query construction.

**Contract**: `describe("listFlashcards", ...)` with:

- No search term → `.or()` is NOT called on the query (oracle: `if (search)` guard, line 47)
- Search with `%` → escaped to `\%` in the ILIKE pattern (oracle: ILIKE wildcard escaping)
- Search with `_` → escaped to `\_` (oracle: ILIKE single-char wildcard)
- Search with `,` → escaped to `\,` (oracle: PostgREST filter syntax)
- Search with `.` → escaped to `\.` (oracle: PostgREST filter syntax)
- Page 1, pageSize 10 → range(0, 9) (oracle: pagination formula lines 37-38)
- Page 2, pageSize 10 → range(10, 19) (oracle: pagination formula)
- Supabase error → throws "Failed to list flashcards: {msg}" (oracle: lines 55-57)
- Count is null → totalCount defaults to 0 (oracle: line 59 `count ?? 0`)
- totalPages computation → `Math.ceil(totalCount / pageSize)` (oracle: line 66)

#### 4. `updateFlashcard` tests

**File**: `src/lib/services/flashcards.test.ts`

**Intent**: Test PGRST116-to-NotFoundError mapping and generic error propagation.

**Contract**: `describe("updateFlashcard", ...)` with:

- Successful update → returns updated Flashcard from mock (happy path)
- PGRST116 error → throws `NotFoundError("Flashcard not found")` (oracle: lines 85-87)
- Other Supabase error → throws "Failed to update flashcard: {msg}" (oracle: line 88)

#### 5. `deleteFlashcard` tests

**File**: `src/lib/services/flashcards.test.ts`

**Intent**: Test the same PGRST116/NotFoundError pattern and verify void return.

**Contract**: `describe("deleteFlashcard", ...)` with:

- Successful delete → returns void, no throw (happy path)
- PGRST116 error → throws `NotFoundError("Flashcard not found")` (oracle: lines 104-106)
- Other Supabase error → throws "Failed to delete flashcard: {msg}" (oracle: line 107)
